# 04 - Godot 服务器架构深度解析

> **源码版本**：Godot 4.8.dev（master 分支，2026-08-26）
> **证据等级**：A（除非另行标注）

---

## 1. 模块概述

Godot 的服务器架构是其工程设计的精华所在。`servers/` 目录定义了一组抽象接口（RenderingServer、PhysicsServer2D/3D、AudioServer、DisplayServer、TextServerManager、NavigationServer 等），将上层场景逻辑与底层硬件后端彻底解耦。这种设计使得 Godot 能够：在同一套上层代码下，支持多种图形 API（Vulkan、Metal、OpenGL ES）、多种物理引擎（GodotPhysics、Box2D、Bullet）、多种音频后端（WASAPI、CoreAudio、PulseAudio）。

服务器架构的核心是三层抽象：**Server 接口层**（定义抽象 API）、**Backend 实现层**（提供具体实现）、**RID 资源管理层**（跨层引用资源）。上层代码通过 Server 接口创建 RID，Server 内部将 RID 映射到 Backend 的实际对象。这种设计使得上层完全不感知 Backend 的存在，Backend 可以自由替换。

本章节将深入分析服务器架构的设计模式、多线程模型、以及各服务器的具体实现。

### 3.2 RID 在服务器中的角色

RID 是连接上层与 Server 的唯一桥梁。上层代码：

```cpp
// 上层（CanvasItem）
RID ci = RenderingServer::get_singleton()->canvas_item_create();
RenderingServer::get_singleton()->canvas_item_set_transform(ci, transform);
RenderingServer::get_singleton()->canvas_item_add_rect(ci, rect, color);
// 上层只持有 RID，不知道内部实现
```

Server 内部：

```cpp
// Server 接口层
RID RenderingServer::canvas_item_create() {
    // 内部创建 CanvasItem 对象
    CanvasItem *ci = memnew(CanvasItem);
    // 注册到 RID_Owner，返回 RID
    return canvas_item_owner.make_rid(ci);
}

void RenderingServer::canvas_item_set_transform(RID p_item, const Transform2D &p_transform) {
    // 通过 RID 取回对象
    CanvasItem *ci = canvas_item_owner.get_or_null(p_item);
    ERR_FAIL_NULL(ci);
    // 修改对象
    ci->transform = p_transform;
}
```

### 3.3 WrapMT 多线程包装模式

> **证据等级 A**：基于 `servers/physics_2d/physics_server_2d_wrap_mt.h` 验证。

对于需要独立线程的服务器（如物理），Godot 使用 WrapMT 模式包装：

```cpp
// servers/physics_2d/physics_server_2d_wrap_mt.h（简化）
class PhysicsServer2DWrapMT : public PhysicsServer2D {
    PhysicsServer2D *physics_2d_server; // 实际实现
    CommandQueueMT command_queue;        // 跨线程命令队列
    Thread::ID thread_id;                // 物理线程 ID
    bool exit = false;
    bool step_thread_up = false;

    // 包装方法：将调用放入队列，由物理线程执行
    virtual RID space_create() override {
        // 同步调用：等待物理线程执行
        RID ret;
        command_queue.push_and_sync(physics_2d_server, &PhysicsServer2D::space_create, &ret);
        return ret;
    }

    virtual void step(float p_delta) override {
        // 异步调用：放入队列，立即返回
        command_queue.push(physics_2d_server, &PhysicsServer2D::step, p_delta);
    }
    // ...
};
```

WrapMT 的核心思想：

- **读操作**：通常同步执行（`push_and_sync`），等待结果
- **写操作**：通常异步执行（`push`），放入队列
- **步进操作**：异步，由物理线程在固定步长执行

这种设计使得上层代码无需关心线程同步，WrapMT 自动处理。

- `viewport_create()` / `viewport_set_size()` / `viewport_set_active()`

// WrapMT 包装：
void PhysicsServer2DWrapMT::body_set_state(RID p_body, BodyState p_state, const Variant &p_variant) {
    // 放入命令队列，由物理线程执行
    command_queue.push(physics_2d_server, &PhysicsServer2D::body_set_state, p_body, p_state, p_variant);

// 物理线程在 step() 前处理队列
void PhysicsServer2DWrapMT::step(float p_delta) {
    // 同步命令队列
    command_queue.wait_and_flush();
    // 执行物理步进
    physics_2d_server->step(p_delta);
}

## 8. 线程模型

### 8.1 主线程服务器

以下服务器在主线程运行：

- **RenderingServer**：命令提交在主线程，GPU 执行异步
- **DisplayServer**：事件处理在主线程
- **TextServerManager**：文本布局在主线程
- **NavigationServer**：同步执行（除非使用异步导航）

### 8.2 独立线程服务器

以下服务器有独立线程：

- **PhysicsServer2D/3D**：通过 WrapMT 在独立线程运行
- **AudioServer**：音频混音在独立线程

### 8.3 线程同步机制

- **CommandQueueMT**：物理服务器的命令队列
- **AudioServer 的事件队列**：音频事件跨线程传递
- **MessageQueue**：通用的延迟调用队列
- **Callable::call_deferred**：延迟到主线程执行

### 8.4 线程安全保证

- **RID_Owner<T, true>**：线程安全版本，使用锁保护
- **RenderingServer 的资源**：主线程访问，无需锁
- **PhysicsServer 的资源**：物理线程访问，通过 WrapMT 同步

## 9. 错误处理与日志

### 9.1 RID 错误处理

```cpp
void RenderingServer::canvas_item_set_transform(RID p_item, const Transform2D &p_transform) {
    CanvasItem *ci = canvas_item_owner.get_or_null(p_item);
    ERR_FAIL_NULL(ci); // 无效 RID，打印错误并返回
    ci->transform = p_transform;
}
```

### 9.2 Backend 错误处理

- **GPU 错误**：RenderingDevice 检查 Vulkan/GLES3 返回值，失败时 `ERR_FAIL`
- **物理错误**：参数无效时 `ERR_FAIL_INVALID_PARAM`
- **音频错误**：设备打开失败返回 `ERR_CANT_OPEN`

### 9.3 性能警告

- 渲染对象过多时警告
- 物理对象过多时警告
- 音频总线过深时警告

## 11. 性能考量

### 11.1 RID 开销

- RID 操作（create/get/free）是 O(1)，开销极小
- RID_Owner 内部数组连续，缓存友好
- 无锁版本性能最佳

### 11.2 WrapMT 开销

- 命令队列有锁开销
- 同步调用（`push_and_sync`）需要等待物理线程，有延迟
- 异步调用（`push`）开销小，但有队列管理成本

### 11.3 渲染性能

- **Draw Call 优化**：Forward+ 支持实例化、合批
- **视锥剔除**：减少不可见物体的渲染
- **GPU 驱动渲染**：Forward+ 在 Vulkan 上支持 GPU 驱动管线

### 11.4 物理性能

- **Broadphase**：使用网格或树结构，O(n log n)
- **Narrowphase**：形状对特定优化
- **Solver 迭代**：默认 10 次，可配置

## 13. 常见陷阱

### 13.1 RID 悬空

资源已 free 但 RID 仍被使用。`get_or_null` 返回 nullptr，调用方应检查。

### 13.2 跨线程访问

非线程安全的服务器（如 RenderingServer）不能在非主线程访问。使用 `call_deferred`。

### 13.3 物理回调中修改场景

在 `body_entered` 回调中 `queue_free` 节点可能导致问题。应使用 `call_deferred`。

### 13.4 渲染后端不匹配

项目设置 Forward+ 但硬件不支持 Vulkan。降级到 mobile 或 gl_compatibility。

### 13.5 音频总线循环

总线 A 发送到 B，B 发送到 A，形成循环。AudioServer 会检测并警告。

### 13.6 资源未释放

忘记调用 `free()` 导致资源泄漏。节点 `queue_free()` 会自动释放关联的 RID。
