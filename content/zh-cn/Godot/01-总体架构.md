# 01 - Godot 总体架构

> **源码版本**：Godot 4.8.dev（master 分支，2026-08-26）
> **证据等级**：A（除非另行标注）

---

## 1. 模块概述

Godot Engine 的 C++ 源码采用**严格的分层架构**，整体可归纳为"自底向上的七层基础设施"模型。每一层只能依赖其下层，不允许反向依赖。这种设计使得引擎具备极强的可移植性与可扩展性：同一套上层逻辑（scene/、editor/）可以运行在不同的平台后端（platform/、drivers/）之上，而无需修改业务代码。

理解 Godot 的总体架构，关键在于把握三个维度：

第一，**纵向分层**。从最底层的平台抽象（platform/、drivers/）到最顶层的编辑器（editor/），Godot 将功能切分为七个清晰的层次。每一层都有明确的职责边界，层与层之间通过定义良好的抽象接口通信。这种分层并非形式主义的代码组织，而是经过多年演进的工程决策——它使得 Godot 能够同时支持桌面、移动、Web、主机等多平台，且每个平台只需实现 platform/ 层的接口。

第二，**横向基础设施**。除了纵向分层，Godot 还有一套贯穿所有层的横向基础设施，包括 Object 对象系统、Variant 动态类型、ClassDB 反射系统、RID 资源句柄、内存管理（memnew/memdelete）、错误处理宏等。这些基础设施是 Godot 的"语言扩展"——它们让 C++ 具备了类似动态语言的反射、序列化、脚本绑定能力，同时保持了 C++ 的性能。

第三，**模块化扩展**。Godot 将可选功能（GDScript、C#、导航、WebRTC 等）组织为独立的 modules/，每个模块通过统一的 register_types.cpp 接口接入引擎。这种设计使得引擎核心保持精简，同时允许按需编译。

本教材将 Godot 源码划分为以下七大目录（层），每一层对应一个明确的职责域：

| 目录 | 层级 | 职责 | 依赖方向 |
|------|------|------|----------|
| `platform/` | L1 | 操作系统抽象（窗口、输入、文件、线程） | 仅依赖 core/ |
| `drivers/` | L1 | 硬件后端驱动（图形 API、音频 API） | 仅依赖 core/、servers/ 接口 |
| `core/` | L2 | 核心库（Object、Variant、容器、数学、IO） | 无外部依赖（除 thirdparty/） |
| `servers/` | L3 | 服务器抽象（渲染、物理、音频、文本） | 依赖 core/ |
| `scene/` | L4 | 场景系统（Node、SceneTree、资源） | 依赖 core/、servers/ |
| `main/` | L5 | 引擎入口与主循环 | 依赖 core/、servers/、scene/、platform/ |
| `modules/` | L4.5 | 可选功能模块 | 依赖 core/、servers/、scene/ |
| `editor/` | L6 | 编辑器（仅 TOOLS_ENABLED） | 依赖所有下层 |

## 4. 核心类与职责

### 4.1 core/ 层：引擎的"语言扩展"

core/ 是 Godot 的基础库，它不依赖任何其他引擎层（仅依赖 thirdparty/ 的第三方库）。这一层的设计目标是：**为 C++ 提供一套面向游戏引擎的高级抽象，使其具备动态语言的部分能力**。

最核心的类是 `Object`（`core/object/object.h:60`）。它是所有可暴露给脚本系统的类的根基类。Object 提供了以下关键能力：运行时类型识别（通过 ClassDB）、动态属性访问（set/get）、方法调用（callp）、信号系统（emit_signal/connect）、通知机制（notification）、脚本绑定（script_instance）、元数据（metadata）。任何一个 C++ 类只要继承 Object 并使用 GDCLASS 宏，就能自动获得这些能力，并可被 GDScript、C# 等脚本语言访问。

与 Object 配套的是 `Variant`（`core/variant/variant.h:94`）。Variant 是 Godot 的动态类型，类似 Python 的变量或 JavaScript 的 var。它内部使用 union 存储 27 种类型的数据，从基本的 bool/int/float/string 到复杂的 Object*/Dictionary/Array。Variant 是脚本系统与 C++ 之间的数据桥梁——所有跨语言边界的参数传递都通过 Variant 完成。

`ClassDB`（`core/object/class_db.h`）是 Godot 的反射系统核心。它在引擎启动时收集所有类的元信息（类名、父类、方法、属性、信号、常量），并在运行时提供查询服务。ClassDB 使得 GDScript 中的 `obj.method()` 调用能够路由到正确的 C++ 方法，使得编辑器能够自动显示节点的属性面板，使得序列化系统能够保存/加载对象。

`RefCounted`（`core/object/ref_counted.h:42`）继承自 Object，为子类提供自动引用计数。所有资源类（Resource、Texture、Material、Mesh 等）都继承 RefCounted，配合 `Ref<T>` 智能指针实现自动内存管理。

`RID`（`core/templates/rid.h:42`）是一个 64 位句柄，用于跨层引用底层资源。上层代码持有 RID，底层通过 RID_Owner<T> 管理实际对象。这种设计解耦了上层与底层实现，使得渲染服务器可以透明地切换 Vulkan/GLES3 后端。

### 4.2 servers/ 层：抽象服务接口

servers/ 层定义了引擎的"服务接口"——它是一组纯虚抽象类，规定了渲染、物理、音频、文本等子系统的 API 契约。实际实现由 drivers/（如 RenderingDeviceVulkan）或 modules/（如 bullet 物理模块）提供。

`RenderingServer`（`servers/rendering/rendering_server.h:64`）是最复杂的服务器，定义了数百个纯虚方法，涵盖纹理、着色器、材质、网格、光源、相机、视口等所有渲染相关操作。它本身是抽象的，具体实现由 `RendererRD`（基于 RenderingDevice 的现代渲染器）提供。

`PhysicsServer2D`（`servers/physics_2d/physics_server_2d.h:42`）和 `PhysicsServer3D` 定义了物理模拟的接口。它们支持通过 GDExtension 替换后端（如 Box2D、Bullet）。

`DisplayServer`（`servers/display/display_server.h`）管理窗口、输入事件、剪贴板、光标等与操作系统交互的功能。每个平台（windows/linux/macos/...）提供具体实现。

`AudioServer`（`servers/audio/audio_server.h`）管理音频总线、效果、播放。

`TextServer`（`servers/text/text_server.h`）抽象了字体渲染与文本布局，支持多后端（如 AdvancedTextServerFallback、AdvancedTextServerAdvanced）。

### 4.3 scene/ 层：场景图与节点系统

scene/ 层构建在 core/ 和 servers/ 之上，提供了游戏开发者最常接触的 API：Node、SceneTree、各种节点类型、资源系统。

`Node`（`scene/main/node.h`）是所有场景节点的基类。它继承 Object，提供了场景树管理（parent/children）、生命周期通知（ENTER_TREE/READY/PROCESS 等）、进程模式（PROCESS_MODE_INHERIT/ALWAYS/DISABLED）、分组、信号连接到节点路径等能力。Node 是 Godot 游戏开发的核心组织单元。

`SceneTree`（`scene/main/scene_tree.h:89`）继承 MainLoop，是引擎运行时的"世界容器"。它持有根 Window，管理所有节点的树形结构，并驱动每帧的 process/physics_process 调用。SceneTree 是 MainLoop 的具体实现——引擎启动后，OS::run() 会调用 SceneTree 的 initialize/process/finalize。

`CanvasItem`（`scene/main/canvas_item.h`）是所有 2D 绘制节点的基类（Node2D、Control 都继承它），提供 2D 变换、绘制命令、排序等能力。

`Viewport`（`scene/main/viewport.h`）定义了渲染目标，可以是 Window、子视口或纹理。所有渲染都发生在某个 Viewport 内。

`Resource`（`core/io/resource.h`，继承 RefCounted）是所有可序列化资源的基类。Texture、Material、Mesh、Font、AudioStream 等都继承 Resource，可通过 ResourceLoader/ResourceSaver 加载/保存。

### 4.4 main/ 层：引擎入口与主循环

main/ 层是引擎的"指挥中心"，负责启动流程、主循环驱动、关闭流程。

`Main` 类（`main/main.cpp`）是引擎的核心控制器，提供四个静态方法：`setup()`（初始化阶段 1，创建 OS、解析参数、注册类型）、`start()`（初始化阶段 2，创建服务器、加载主场景）、`iteration()`（每帧调用，驱动主循环）、`cleanup()`（关闭，释放所有资源）。

### 4.5 platform/ 层：操作系统适配

platform/ 层为每个支持的平台提供 OS 抽象的具体实现。每个平台目录包含：入口函数（main/WinMain）、OS 子类（如 OS_Windows）、DisplayServer 子类、平台特定的驱动。

`OS`（`core/os/os.h`）是操作系统抽象基类，定义了文件系统、时间、线程、命令行、环境变量等接口。每个平台提供子类实现。

### 4.6 drivers/ 层：硬件后端驱动

drivers/ 层提供具体的硬件后端实现，主要是图形 API（vulkan、gles3）和音频 API。这些驱动实现 servers/ 层定义的接口，但不直接被上层使用——上层总是通过 RenderingServer 等抽象接口访问。

### 4.7 modules/ 层：可选功能模块

modules/ 层包含所有可选功能，每个模块通过 `register_types.cpp` 接入引擎。模块分为四级初始化：CORE、SERVERS、SCENE、EDITOR，确保依赖顺序正确。重要模块包括 gdscript（GDScript 语言）、mono（C# 支持）、navigation（导航）、bullet/box2d（物理后端）等。

### 5.3 主循环驱动流程

> **证据等级 A**：基于 `main/main.cpp` 的 `iteration()` 方法验证。

每帧的执行流程（简化）：

```
Main::iteration()  (main.cpp)
│
├── 1. DisplayServer::process_events()      ← 处理窗口/输入事件
│
├── 2. PhysicsServer2D/3D::step()           ← 物理模拟（固定步长）
│       └── 触发 _physics_process 通知
│
├── 3. SceneTree::process(delta)            ← 场景逻辑更新
│       ├── 遍历节点树，发送 NOTIFICATION_PROCESS
│       ├── 处理信号
│       └── 处理延迟调用（call_deferred）
│
├── 4. RenderingServer::draw()              ← 渲染
│       ├── 更新场景数据
│       ├── 提交渲染命令到 GPU
│       └── 交换缓冲区
│
├── 5. AudioServer::update()                ← 音频更新
│
├── 6. 处理 MessageQueue（延迟调用队列）
│
└── 7. 处理 Object::predelete 队列（memdelete 延迟）
```

## 6. 与其他模块的交互

### 6.1 core/ 与其他层的交互

core/ 是最底层，不依赖其他引擎层。但所有上层都依赖 core/。core/ 通过以下机制为上层提供服务：

- **Object 系统**：上层类继承 Object 获得反射能力
- **Variant**：上层通过 Variant 与脚本系统交换数据
- **ClassDB**：上层通过 GDREGISTER_CLASS 注册自己的类
- **RID**：上层通过 RID 引用底层资源
- **容器与数学库**：上层直接使用 Vector、HashMap、Vector3 等

### 6.2 servers/ 与 drivers/ 的交互

servers/ 定义抽象接口，drivers/ 提供实现。例如：

- `RenderingServer`（抽象）← `RendererRD`（实现）← `RenderingDevice`（抽象）← `RenderingDeviceDriverVulkan`（实现，在 drivers/）
- `PhysicsServer2D`（抽象）← `PhysicsServer2DGodot`（实现，在 modules/）或 `PhysicsServer2DExtension`（GDExtension）

### 6.3 scene/ 与 servers/ 的交互

scene/ 层的节点通过 servers/ 提供的接口操作底层资源。例如：

- `Sprite2D`（scene/2d/）通过 `RenderingServer::canvas_item_add_texture_rect()` 提交绘制命令
- `RigidBody2D`（scene/2d/）通过 `PhysicsServer2D::body_create()` 创建物理体
- `Camera3D`（scene/3d/）通过 `RenderingServer::camera_set_transform()` 更新相机

### 6.4 main/ 与所有层的交互

main/ 是"胶水层"，它协调所有层的初始化与销毁：

- 启动时调用各层的 `register_*_types()`
- 创建 OS（platform/）、DisplayServer、RenderingServer 等单例
- 创建 SceneTree（scene/）作为主循环
- 每帧调用 `iteration()` 驱动所有子系统

## 7. 内存与生命周期

> **证据等级 A**：基于 `core/os/memory.h` 与 `core/object/ref_counted.h` 验证。

### 7.1 内存分配：memnew / memdelete

Godot 不直接使用 `new`/`delete`，而是使用自定义的 `memnew`/`memdelete` 宏（`core/os/memory.h`）。这些宏在分配时记录内存统计信息，便于调试内存泄漏与跟踪用量。

```cpp
// 分配单个对象
Object *obj = memnew(Object);
memdelete(obj);

// 分配数组
int *arr = memnew_arr(int, 100);
memdelete_arr(arr);
```

`memnew` 实际上调用 `new` 但包装了统计逻辑。在 DEBUG 模式下，它会记录调用位置、分配大小，便于 `Memory::dump()` 输出内存报告。

### 7.2 对象生命周期：Object

Object 的生命周期由创建者管理。普通 Object（非 RefCounted）必须由 `memdelete` 显式释放。生命周期关键节点：

```
构造函数执行
    │
    ▼
_postinitialize()  (object.cpp:191)
    │  发送 NOTIFICATION_POSTINITIALIZE (0)
    │  此时对象的类信息已就绪，可安全调用虚函数
    ▼
正常使用阶段
    │  可接收 notification()、emit_signal()、call() 等
    ▼
_predelete()  (object.cpp:138)
    │  发送 NOTIFICATION_PREDELETE (1)
    │  子类可在此清理资源、断开连接
    │  若返回 false，取消删除
    ▼
NOTIFICATION_PREDELETE_CLEANUP (3)
    │  最终清理，不可逆
    ▼
析构函数执行
    │  释放 script_instance、extension 等
    ▼
memdelete 释放内存
```

### 7.3 引用计数：RefCounted

RefCounted 子类通过引用计数自动管理生命周期。`Ref<T>` 是智能指针，构造时增引用，析构时减引用，归零时自动 `memdelete`。

```cpp
// core/object/ref_counted.h:42
class RefCounted : public Object {
    SafeRefCount refcount;
    // bool _ref();   ← 增引用，返回是否成功
    // bool _unref(); ← 减引用，归零返回 true 触发删除
};

// 使用
Ref<Image> img = memnew(Image);  // 引用 = 1
Ref<Image> img2 = img;           // 引用 = 2
img2.unref();                    // 引用 = 1
img.unref();                     // 引用 = 0 → memdelete(img)
```

### 7.4 RID 资源生命周期

底层资源（如 GPU 纹理）通过 RID 管理。上层持有 RID，底层通过 RID_Owner<T> 跟踪：

```
创建：RenderingServer::texture_2d_create()
    → 内部 memnew(Texture)
    → RID_Owner<Texture>::make_rid(texture)
    → 返回 RID

使用：RenderingServer::texture_2d_update(rid, ...)
    → RID_Owner::get_or_null(rid) 取回 Texture*
    → 更新数据

销毁：RenderingServer::free(rid)
    → RID_Owner::free(rid) 取回 Texture*
    → memdelete(texture)
```

## 8. 线程模型

> **证据等级 B**：基于源码结构与宏定义推断。

### 8.1 主线程模型

Godot 的场景系统（Node、SceneTree）主要在主线程运行。大多数 API 假设单线程访问，跨线程访问需要特殊处理。

### 8.2 服务器多线程

部分服务器支持多线程后端，通过 `*WrapMT` 模式实现：

```
PhysicsServer2DWrapMT (servers/physics_2d/physics_server_2d_wrap_mt.h:63)
├── 继承 PhysicsServer2D
├── 内部持有 PhysicsServer2D *physics_server_2d（实际后端）
├── CommandQueueMT command_queue（命令队列）
├── 独立线程执行实际物理模拟
└── 主线程调用 → 封装为命令 → 入队 → 物理线程执行
```

这种模式将跨线程调用封装为命令队列，避免锁竞争。`ASYNC_COND_PUSH` 宏判断调用者是否在服务器线程，决定同步还是异步。

### 8.3 工作线程池

`WorkerThreadPool`（`core/object/worker_thread_pool.h`）提供通用任务并行能力，用于资源加载、纹理压缩等可并行任务。

## 9. 错误处理与日志

> **证据等级 A**：基于 `core/error/error_macros.h` 验证。

### 9.1 错误处理宏

Godot 使用宏统一错误处理，主要分三类：

```cpp
// 1. 条件失败 → 返回（无返回值函数）
ERR_FAIL_COND(condition);
ERR_FAIL_COND_MSG(condition, "message");

// 2. 条件失败 → 返回指定值
ERR_FAIL_COND_V(condition, retval);
ERR_FAIL_COND_V_MSG(condition, retval, "message");

// 3. 条件失败 → 中止程序（严重错误）
ERR_FAIL_COND_MSG(condition, "message");
CRASH_COND(condition);
CRASH_NOW_MSG("message");
```

### 9.2 日志输出

```cpp
print_line("普通日志");           // 标准输出
print_verbose("详细日志");        // 仅 verbose 模式
WARN_PRINT("警告");              // 警告
WARN_PRINT_ED("编辑器警告");     // 仅编辑器
ERR_PRINT("错误日志");           // 错误（不中止）
```

### 9.3 断言

```cpp
DEV_ASSERT(condition);   // 仅 DEV_ENABLED 时检查
DEBUG_ASSERT(condition); // 仅 DEBUG_ENABLED 时检查
```

## 11. 性能考量

### 11.1 内联优化

Godot 大量使用 `_FORCE_INLINE_`（强制内联）与 `_ALWAYS_INLINE_` 宏，对热点函数（如 Variant 访问、RID 解引用、容器操作）进行内联优化。

### 11.2 栈分配优先

为减少堆分配，Godot 使用 `LocalVector`（预分配栈空间）与栈数组。例如 `Object::emit_signalp` 在槽位 ≤5 时使用栈数组（`object.cpp:1263`）：

```cpp
// object.cpp:1261-1268
constexpr int MAX_SLOTS_ON_STACK = 5;
alignas(Callable) uint8_t slot_callable_stack[sizeof(Callable) * MAX_SLOTS_ON_STACK];
uint32_t slot_flags_stack[MAX_SLOTS_ON_STACK];
// ... 超过 5 个才 memalloc
```

### 11.3 写时复制

`CowData`（`core/templates/cowdata.h`）实现写时复制，用于 String、PackedArray 等容器的共享数据。

### 11.4 字符串驻留

`StringName`（`core/string/string_name.h`）是驻留字符串，相同内容只存一份，比较时只需比较指针。用于类名、方法名、信号名等高频比较场景。

## 13. 常见陷阱

### 13.1 循环引用

RefCounted 对象间的循环引用会导致内存泄漏。解决方案：使用 `WeakRef` 打破循环，或重新设计为单向依赖。

### 13.2 跨线程访问 Node

Node 系统非线程安全。跨线程操作 Node 必须使用 `call_deferred` 或 `MessageQueue`。

### 13.3 在构造函数中调用虚函数

Object 构造期间虚函数表未完全就绪。`_postinitialize()`（`object.cpp:191`）在构造后发送 `NOTIFICATION_POSTINITIALIZE`，此时才可安全调用虚函数。

### 13.4 RID 悬空

RID 持有者释放后，RID 变为悬空。使用前应检查 `RID::is_valid()`，或确保 RID 生命周期与资源同步。

### 13.5 信号连接未断开

连接到已删除对象的信号会导致崩溃。Object 析构时会自动断开其所有连接，但跨服务器的连接需手动管理。
